## 1. Target — what "done" means

**Product:** a searchable, verifiable digital English→Farsi legal dictionary built
from a ~430-page **[verify]** printed book. A user looks up an English headword and
gets its **Farsi equivalent + English definition**, with the **source-image crop**
viewable per entry for legal verifiability.

**Two governing insights (do not drift from these):**
1. This is an **extraction-fidelity** problem wearing an AI-app costume. It succeeds
   or fails at turning page images into clean, correctly *segmented* entries.
2. The endgame is **retrieval, not fine-tuning** — verifiable, correctable, and it
   doesn't confabulate term equivalences.

**Definition of done — CORE (Phases 2–4):**
- Every printed entry in the corpus is extracted as exactly one validated record,
  fields in the right slots, Farsi normalized, source crop stored.
- Deterministic search (exact / prefix / fuzzy on the English headword; Farsi
  keyword on the equivalent) returns the correct entry, bidirectional UI, crop
  visible per result.

**Definition of done — OPTIONAL (Phase 5, only if pursued):** a grounded RAG chatbot
that meets the RAG Quality Bar's own gates, with an explicit refusal path.

**Non-goals (explicitly out of scope):** fine-tuning as an accuracy mechanism; a
full observability platform; corrective/self-RAG; named RAG metrics
(precision/recall/faithfulness) unless Phase 5 independently needs them.

## 2. Architecture (the pipeline and its seams)

```
[lossless capture] → [Google Vision OCR] → data/output/*.json  (words + bbox + lang + conf)
   → [parser: readVisionWords → column split @x=1100 → Y-group into lines → script-tag]   ← DETERMINISTIC
   → [LLM corrector: segment lines into entries, fix OCR, resolve bidi]                    ← MODEL (config.ts)
   → [normalize (NFC + Arabic→Persian)] → [Zod Tier-1 + Tier-2] → [cross-record checks]
   → [Drizzle → Postgres] → [retrieval search API] → [UI + source-crop verify]
                                          |
                         (optional Layer 2: embeddings + pgvector + RAG chatbot)
```

**The critical seam** is between the deterministic parser and the LLM corrector. The
parser hands the LLM a per-column, reading-ordered, script-tagged **transcript**
(`ColumnTranscript` → `Line[]`). The LLM returns `CorrectedEntry[]` with
`line_indices` back-references so the parser can recover each entry's source bbox
and confidence. Keeping this seam clean keeps the LLM's scope tight.

## 4. Data contract (canonical)

The `Entry` record (Guide §10) is the contract every stage must satisfy. Direction
is **English headword → Farsi equivalent → English definition**. Key fields:
`headword_en`, `headword_normalized` (lowercased/stripped, for exact+prefix search),
`translation_fa` (Arabic-script, normalized), `definition_en`, `pos` (Tier-1 enum
from a known set — **[verify]**, derive from the book's front-matter key),
`source_image` (page, column, bbox = union of the entry's word boxes),
`is_continuation` (runover flag), `needs_review`, `confidence`.

Validation is **two-tier + cross-record**:
- **Tier 1 (structural)** — generated by `drizzle-zod` from the table. Field
  presence, types, enums. Drift-proof.
- **Tier 2 (domain)** — hand-written refinements. **Script isolation is the real
  language check** (Vision mis-tags English, so `languageCode` is untrusted).
  Diacritic/dot sanity routes borderline records to `needs_review`, never
  auto-rejects.
- **Cross-record** — runs outside Zod: **alphabetical-order continuity** across the
  corpus, which **must tolerate runover continuations**.
- **Normalize before validating** (NFC + Arabic→Persian), or fine characters
  produce false failures.

## 5. Phase plan — goals, gates, exit artifacts

Each phase has a **gate**: an objective bar that must be met before the next phase
starts. Gates exist to prevent scaling an unproven step.

### Phase 2 — Parser POC
**Goal:** prove entry reconstruction on the 3 messy pages (05–07) before scanning more.
**Work:** wire the LLM corrector to the deterministic transcript; run the full
`parsePage` on 05–07; measure against a hand-keyed answer key.
**Gate:** thresholds live as tunable consts in `src/eval/thresholds.ts` — they are
**provisional** and **calibrated from T5's first real measurement**, never guessed
from current data (v1 data shows only OCR confidence, not accuracy/CER).
- Entry-reconstruction accuracy ≥ `ENTRY_RECONSTRUCTION_ACCURACY_MIN` (default 0.95,
  provisional).
- Persian CER ≤ `PERSIAN_CER_MAX` (default 0.02, provisional).
- All five hard-case categories demonstrably handled: cross-page runover,
  cross-references (`<`/`>`), `مثال` examples, mixed-language blocks, the section
  header `A`.
**Exit artifact:** an accuracy report (metrics + the failure list) committed under `docs/`.

### Phase 3 — Capture, backup, full extraction
**Preconditions (do BOTH before mass scanning):**
- **Back up `data/`** to durable storage — the source is irreplaceable and currently
  in one place. Evidence of the backup required.
- **Fix capture**: lossless (PNG/TIFF), consistent 300–600 DPI, de-warped; re-scan
  the existing 3 pages losslessly too.
**Work:** batch capture → Vision → parser → corrector → normalize → Zod → Drizzle insert.
**Gate:**
- Full corpus extracted; alphabetical-continuity check passes corpus-wide (tolerating
  runover); `needs_review` rate ≤ **[verify]**%; page count reconciles two ways.
- Layout re-checked on sampled non-"A" sections (later letters, front matter,
  appendices) before trusting the parser corpus-wide.
**Exit artifact:** populated Postgres + a validation summary report.

### Phase 4 — Retrieval search product (CORE DELIVERABLE)
**Goal:** the actual product. Deterministic lookup, no embeddings.
**Work:** exact + prefix search on `headword_en`; fuzzy via `pg_trgm`; Farsi keyword
search on `translation_fa`; bidirectional UI (`dir="rtl"` for Farsi); source crop
viewable per result.
**Gate:** on a held-out query set, correct entry returned for exact/prefix/fuzzy;
crop renders; RTL/LTR correct.
**Exit artifact:** deployed searchable app.

### Phase 5 — Semantic layer + RAG chatbot (OPTIONAL)
**Only if** natural-language interaction is actually needed. **This is where the RAG
Quality Bar becomes the spec.** Sequencing is non-negotiable: **instrument first →
triage logs into failure modes → derive evals from those failure modes → only then
add hybrid/rerank and prove they helped.**
**Domain cautions:** grounding reduces but doesn't eliminate hallucination — keep the
source-crop verification and an explicit **refusal / "not in the dictionary"** path.
Entries are naturally atomic (one entry ≈ one chunk), which sidesteps most
chunk-boundary failure modes — use that.
**Gate:** the RAG Quality Bar's own deliverable — a failure-mode table populated
**from real traces** + a green eval harness.

## 7. LLM correction — I/O contract (immediate next implementation)

- **Input:** one `ColumnTranscript` = `{ page_number, column, lines[] }`, each `Line`
  = `{ text, script (latin|farsi|mixed|other), yTop, bbox, avgConfidence, words[] }`,
  in reading order.
- **Output:** `CorrectedEntry[]`, each = `{ headword_en, translation_fa,
  definition_en, pronunciation, pos, is_continuation, raw_ocr_snippet, line_indices }`.
- **Rules:** the LLM is a **corrector, not an oracle** — its output passes the same
  Zod + cross-record gate. It must segment entries, fix OCR errors, resolve bidi
  mixed lines, and classify runover vs cross-ref vs example. Model is chosen in
  `src/llm/config.ts` (default `frontier`); exact model id is **[verify]**, set via
  `LLM_MODEL`.

## 8. Handoff protocol (how §9 tasks are run)

Every task is executed under `work-protocol-01.md`: echo the requirement; produce
exactly it (no variant); **evidence or it didn't happen** (paste raw output, paths,
diffs); numbers tie out twice; no memory-based facts; scope is a wall; end with a
binary compliance table. A substituted/approximated result presented as done is
worse than no result — mark `CANNOT COMPLY` / `PARTIAL` honestly.

**Standing rules for every worker handoff (in addition to the Work Protocol):**
1. **TDD** — write the failing test first, then the code that makes it pass. No
   implementation lands without a test that exercises it.
2. **Enable the `ponytail` skill** before starting. *(Confirm exact skill name — see
   note below.)*
3. **Produce a results/verification document** for the handed-off work, stating
   **deterministic, machine-checkable pass/fail criteria** (exact commands, exact
   expected outputs/counts) — not prose claims. Those criteria are the acceptance
   gate; "it works" is not acceptance.

## 11. Active risks (from Guide §12, live only)

- **No backup; JPEG-only source** → T7 + T8, before any scaling.
- **Farsi dot/diacritic loss** → lossless capture + diacritic-sanity validation.
- **Vision mis-tags English / blocks ≠ entries** → already mitigated in parser
  (script + coordinates, not `languageCode` / blocks); keep enforced via Tier-2.
- **Runover across pages** → `is_continuation` + runover-tolerant continuity check.
- **Over-engineering the chatbot** → Layer 2 stays optional; retrieval is the deliverable.
